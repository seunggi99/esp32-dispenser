# 트러블슈팅 기록

개발 중 겪은 문제와 원인, 조치를 증상 단위로 정리한다.

## OLED가 I2C 스캔에서 안 잡힘

**증상**: `Wire.beginTransmission()`으로 주소 1~126 전부 스캔해도 응답이 없음
(`no i2c device`).

**원인**: 배선 자체(SDA=21, SCL=22, VCC=3V3, GND)는 코드와 일치했지만, 실제로는
접촉 불량 또는 SDA/SCL 핀 자체가 물리적으로 잘못 꽂혀 있었음.

**조치**: `Wire.begin(21, 22)`뿐 아니라 SDA/SCL을 바꿔서도 한 번 더 스캔하도록
펌웨어에 폴백을 추가해 배선 실수를 코드 레벨에서도 잡을 수 있게 함. 이후 재배선으로
`0x3C`에서 정상 응답 확인.

## 시리얼 모니터에 무한 재부팅처럼 보이는 로그가 반복됨

**증상**: `pio device monitor` 대신 파이썬 `pyserial`로 시리얼을 읽었을 때, 짧은
바이트 패턴이 초당 수백~수천 번 반복되는 것처럼 보여 "장비가 브라운아웃으로 무한
재부팅 중"으로 오인함. 초당 수백 KB는 115200bps로 물리적으로 불가능한 처리량이었음.

**원인**: 실제 재부팅이 아니라, macOS USB-시리얼 드라이버의 버퍼 잔여물이었음.
이전 테스트(잘못된 보드레이트로 읽기, 반복적인 포트 open/close)에서 커널/드라이버
레벨 버퍼에 쌓인 데이터가, 이후 새로 연 세션에서 한꺼번에 쏟아져 나온 것.
`reset_input_buffer()`는 pyserial 레벨 버퍼만 비우고 드라이버 레벨 버퍼는 못 비움.

**진단 방법**: DTR/RTS를 토글해 보드를 명시적으로 리셋한 직후 곧바로 읽으면
(`ets Jul 29 2019 ...` 부트 로그부터 시작) 항상 깨끗하게 읽혔음 — 이게 신뢰할 수
있는 유일한 방법이었음. 반대로 "그냥 몇 초간 수동" 읽기는 매번 재현성이 달랐음.

**교훈**: 이 환경에서 시리얼 상태를 확인할 땐 반드시 리셋 펄스 직후 즉시 캡처할 것.
장시간 수동 대기 후 읽은 로그는 신뢰하지 말 것.

## HX711 raw 값이 계속 0으로 고정

**증상**: `ready=1`(HX711 응답 정상)인데 `raw`가 항상 0 또는 -1(0xFFFFFF)로 고정,
로드셀에 힘을 줘도 변화 없음.

**원인**: ESP32 ↔ HX711 통신(DOUT/SCK)은 정상이지만, 로드셀 4선(E+/E-/A+/A-)이
HX711에 제대로 연결되지 않아 브릿지 신호 자체가 안 들어오고 있었음.

**진단 방법**: 로드셀을 HX711에서 분리한 상태로 E+/E-, A+/A- 사이 저항을 멀티미터로
측정 (~1kΩ 근처가 정상). 0Ω(단락) 또는 무한대(단선)면 로드셀 자체 불량, 정상 범위인데
`raw`가 안 움직이면 배선 접촉 문제로 좁혀서 진단.

## MQTT result가 실제로는 왔는데 서버가 타임아웃 처리함

**증상**: 장비는 정상적으로 펌프를 구동하고 result를 보냈는데, 서버 로그에는
`result_timeout=true`로 기록됨.

**원인**: 초기 구현에서는 result 대기 시간과 무게 재측정 시점이 동일한 값
(`duration_ms + stabilization_delay_s`)을 공유했음. MQTT 왕복 지연 + 장비 처리
시간 때문에 실제 result가 이 창을 벗어나 늦게 도착하는 경우가 실측에서 확인됨.

**조치**: result 대기(`result_wait_s`, 기본 10초)와 무게 재측정 시점
(`duration_ms + stabilization_delay_s`)을 분리해서 `asyncio.gather`로 병렬
처리하도록 변경. 무게는 항상 정해진 시점에 재고, result는 그와 무관하게
`result_wait_s`까지 별도로 기다린 뒤 기록만 함 (판정에는 안 씀).

## 실제 운영 서버와 같은 SQLite 파일을 공유한 채로 테스트하다 데이터 초기화

**증상**: 테스트를 위해 `server/app.db`를 `rm -f`로 지웠는데, 그 시점에 이미
`--reload`로 떠 있던 실제 서버가 같은 파일을 쓰고 있어 누적되어 있던 텔레메트리/
명령 이력이 전부 사라짐.

**원인**: 여러 uvicorn 인스턴스(테스트용 + 실사용)가 같은 작업 디렉터리에서
같은 `app.db` 경로를 공유. 포트가 다르다고 해서 DB 파일까지 분리되는 것은 아님.

**교훈**: 격리된 테스트가 필요하면 포트뿐 아니라 실행 디렉터리(또는 `DB_PATH`)도
분리하거나, 먼저 `ps aux | grep uvicorn`으로 이미 떠 있는 프로세스가 있는지 확인할 것.
